# The prototype suite

A different question from the game suite next door. That one hands a model a finished game and asks
for a change; this one hands it a **starter project** and asks it to build something.

The distinction turned out to matter. Two nights of the editing study were spent watching a 9B model
hunt through a codebase for a file, and what got measured was its search strategy — at one point six
identical `find` commands in a row — rather than anything about a scene format. Authoring from a
scaffold removes the search entirely. There is one obvious place to write, and the only question left
is whether the model can write it correctly.

## The same starting line

Every stack begins with the same running project: a lit, turning cube on a ground, a camera, and
nothing else.

| stack | starter |
|---|---|
| `vanilla` | hand-written three.js — one `Prototype` class |
| `r3f` | React Three Fiber — one `Sketch` component |
| `scenoco` | whatever `scenoco init` generates, unmodified except for two `name` attributes |

The scenoco arm is deliberately *the real product*: the scaffold is generated by the shipped
`scenoco init`, comments and all, because the scaffold **is** the onboarding and hiding it would be
measuring a different framework. The other two starters were written to match it — same camera, same
lights, same ground, same 45°/s cube — and carry comments of comparable weight, including the
shape-sizing facts each stack needs. An arm that starts further ahead makes the whole study
worthless, so parity of the starting line is the thing to attack first if you doubt the results.

## The seam

Each arm exports the same three things, and the oracle imports nothing else:

```ts
export interface Sketch {
  scene: Scene;
  step(dt: number): void;
  dispose(): void;
}
export function createSketch(): Promise<Sketch>;
```

`src/harness.ts` is restored before grading and excluded from the diff. It is not the prototype — it
is the contract the prototype is read through, and leaving it writable makes the study forgeable:
an agent that rewrites the seam can satisfy any oracle without building anything.

## What the checks ask

Names and geometry, never a stack's own types — *is the thing there, is it the right shape, is it in
the right place, does it move*. That is the only question three stacks can be asked in the same
words. "Standing on the ground" is measured from a world-space bounding box rather than from
`position`, because a cylinder two units tall rests at `y = 1` and a cube at `y = 0.5`; asking about
the box asks the real question instead of a stack-specific one.

Two guards run around every cell:

- **`pristine.test.ts`** — every task must *fail* on an untouched scaffold. A task that already
  passes is measuring nothing, and this suite refuses to start until all of them fail.
- **`core.test.ts`** — the ground, the block, and the block still turning. No task has any business
  touching those, so anything that breaks them broke the project while extending it.

## Running it

```
npm run bench -- --suite proto --arms vanilla,r3f,scenoco --tasks pillars
```

Cells get five minutes here rather than fifteen, so three stacks on one task is a quarter of an hour
end to end — short enough that a bad design shows up before a night has been spent on it.
